## 0. 一页结论

### 0.1 你问的三个问题

| 问题 | 结论 | 理由（详见章节） |
| --- | --- | --- |
| **HTML/JS 实现，对外开放会不会不安全？** | **会，但根因不是语言。** 有 15 项可量化的风险，其中 4 项是"公网上真能被利用"的 | 浏览器只能跑 HTML/CSS/JS，换后端语言不改变前端；风险在部署细节（Cookie 无 `Secure`、限流可绕过、注册全开放、无安全头、JSON 非原子写）。见 §2 |
| **能否重构成 Java 或 .NET？** | **技术上能，但不划算，本轮不建议。** 建议先做安全加固 + 存储改造，把"重写"作为有触发条件的备选 | 8,915 行里大半是上游行情口径与降级逻辑，重写 8–14 周且最大代价是 14:30 / 19:30 推送漏发的业务风险；零依赖反而是资产。见 §3、§4 |
| **JSON 本地文件改数据库会不会更好？** | **会更好，但要划边界：权威小状态进库，行情快照不进库。** 推荐 SQLite（`node:sqlite`，保持零依赖） | 当前 JSON 是"非原子写 + 解析失败静默回退空表 + 读改写竞态"，这三件事在数据库里都不存在；但 60KB 级别的行情快照是可再生缓存，进库没有收益。见 §5 |

### 0.2 如果只做一件事

**先做 P0-1 / P0-2 / P0-3 / P0-5 这四项（合计约半天）**：Cookie 加 `Secure`、会话 token 只存哈希、关掉开放注册、限流改用不可伪造的真实 IP。这四件事是唯一能真正阻止"公网上被爆破密码 / 被白嫖行情配额 / 会话被嗅探"的动作。

### 0.3 建议推进顺序

```
现在 ──► P0 安全加固（1 天）──► P1 SQLite 存储（3–5 天）──► P2 代码结构（按需）──► P3 重写（待触发）
         不碰前端，逐项可回退        接口契约不变，前端零改动        拆 server.js，补测试        闸门见 §4.3
```

### 1.1 规模与结构

### 1.2 单次请求的链路

```
浏览器 ──► http.createServer (server.js:8753)
            ├─ 解析 URL / 定向：/admin → /admin.html

            ├─ currentUser()：读 sessions.json + users.json（同步 IO，server.js:7633-7646）
            ├─ PUBLIC_API 白名单判断 → 未登录 401

            └─ sendJSON：`Cache-Control: no-store` + `Access-Control-Allow-Origin: *`
```

### 1.5 工程约束

1. **零依赖**是当前最大的工程资产（无供应链漏洞、无 `npm audit` 噪音、升级只跟 Node 版本），任何改造都应尽量保留。
2. **无测试、无 CI**：所有验证靠手工点页面。P1 改存储时，这是最大风险源，必须先补 3 个关键路径测试或手工回放清单（§9）。
3. **版本不一致（已于 2026-11-15 解决）**：本地 Node **v24.14.1**，NAS 已从 **v20.19.4** 升到 **v24.22.3**（装在 `/data/node24`，旧版保留可回滚），`node:sqlite` 在 NAS 上实测可用。
4. **文档与实现不一致**：`README.md:490` 关于默认绑定地址的描述已过时（见 §1.3）。

## 2. 安全风险清单

严重度定义：**高** = 公网可直接利用且后果严重；**中** = 需要前置条件或被攻破后可放大；**低** = 信息泄露 / 加固项。

| # | 严重度 | 风险 | 证据（`server.js`） | 场景与后果 | 修复方式 | 工作量 |
| --- | --- | --- | --- | --- | --- | --- |
| S1 | **高** | 会话 Cookie 无 `Secure` | `7701` | 局域网 / 公共 Wi-Fi 上明文 HTTP，同网设备可抓到 `gp_sid`，30 天有效期 → 直接接管账号 | HTTPS 时下发 `Secure`；会话只存 `sha256(token)`，文件泄露≠可登录 | 1.5 h |
| S2 | **高** | 登录限流可被绕过 | `7783-7786`、`7997-8012` | `clientIp()` 直接取 `X-Forwarded-For` 首段，攻击者每次请求换一个假 IP，即可无限次爆破密码 / 无限刷注册 | 仅可信代理（Cloudflare）下读 `CF-Connecting-IP`，否则用 socket 地址；限流键改 **IP + 用户名**；注册独立限流 | 1 h |
| S3 | **高** | 注册完全开放 | `7538-7545`、`7959` | 公网任何人注册即成普通用户，可读全部 75 个行情接口、消耗上游配额、可能触发东财限频（历史上已发生 502） | `ALLOW_REGISTER=0` 默认关闭；需要时用邀请码；首个账号走 `scripts/superadmin.js` | 1 h |
| S4 | **高** | JSON 非原子写 + 解析失败静默回退 | `7563-7569`、`7571-7574` | 写 `users.json` 时进程被杀 / 断电 → 文件截断；下次启动 `JSON.parse` 抛错被 `catch` 吞掉 → 返回空账号表 → **全员无法登录且日志无任何报错** | 过渡期：写临时文件 + `rename` 原子替换 + 解析失败告警；根治：P1 换 SQLite 事务 | 0.5 h（临时）/ P1（根治） |
| S5 | 中高 | 无任何安全响应头 | 全文 0 命中（CSP/HSTS/XFO/XCTO/Referrer-Policy） | 任何一处 XSS 都能直接调 API 改持仓 / 拿推送密钥；页面可被第三方 iframe 嵌套做点击劫持 | 统一注入 6 个头 + CSP（先 `Report-Only` 观察 2–3 天再强制） | 2 h |
| S6 | 中 | 220 处 `innerHTML` 的 XSS 面 | `public/js/app.js`（全文） | 快讯 / 新闻标题来自上游，`renderNewsList` 已 `esc`（`app.js:873`），其余 200+ 处需逐处确认；漏一处就是存储型 XSS | 统一走 `esc()`；分批审计；CSP 作兜底 | 1 天 |
| S7 | 中 | `ACAO: *` + 无 CSRF/Origin 校验 | `8717`、`8765-8771` | 同站子域被攻破或恶意页面可发起带 Cookie 的 POST（`SameSite=Lax` 只挡跨站 Cookie，不挡同站） | 删除 `ACAO: *`（同源部署不需要）；POST 校验 `Origin` / `Sec-Fetch-Site`（**前端零改动**） | 1 h |
| S8 | 中 | 静态目录前缀比较可绕过 | `8733` | 校验 `file.startsWith(root)`，同名前缀目录（如 `public-evil`）可通过；`decodeURIComponent` 二次解码（`8725`）也易出错 | 改 `path.relative()` 判定 + `..` / 绝对路径拒绝 + 只解码一次 | 0.3 h |
| S9 | 中 | 每个请求 2 次同步读盘 | `7633-7646` | 公网并发下阻塞事件循环，可被低成本放大成 DoS；`sessions.json` 反复全量读写 | 会话 / 账号内存缓存 + 变更失效；P1 后改 SQLite 查询 | 0.5 天 |
| S10 | 中 | webhook 任意地址由服务端请求 | `7238`、`7252` | 管理员账号一旦被拿下，可让服务器请求 NAS 内网任意地址（`192.168.31.x`、`127.0.0.1:9302`）→ SSRF 横向 | 只允许 `https:`；拒绝私网 / 回环 / 链路本地；DNS 解析后再复查 | 1 h |
| S11 | 中 | 1 处上游 `fetch` 无超时 | `2290`（板块清单页；其余 31 处出站调用均已带 `AbortSignal`） | 上游挂起时请求不返回，堆积占内存 | 补 `AbortSignal.timeout(8000~15000)` | 0.2 h |
| S12 | 低中 | 错误响应回显内部信息 | `8802-8808` | 把 `err.message`、`path`、时间直接回给客户端，泄露实现细节 | 对外统一 `{error:'服务暂时不可用', code}`，细节只进日志 | 0.5 h |
| S13 | 低 | 日志打印完整 query | `8800` | 敏感参数（token、webhook）进日志文件 | 日志按白名单脱敏 | 0.3 h |
| S14 | 低 | 管理页公开、健康检查公开 | `8822`、`7544` | `admin.html` 无需登录即可打开（接口仍校验角色，无数据泄露，但暴露结构）；`/api/health` 可被外部探活 | `admin.html` 也纳入登录跳转；`health` 仅返回状态与版本 | 0.5 h |
| S15 | 低 | 局域网明文 HTTP，且默认监听全网卡 | `42-43`（`HOST` 默认 `0.0.0.0`） | 手机 / 同网设备明文传输会话 | 局域网可选 HTTPS（mkcert 自签 + Caddy/Nginx），或把默认值收回 `127.0.0.1` 并显式开启；同步修正 README | 1 h |

### 2.1 三条最该先修的（按"能被利用 + 后果重"排序）

1. **S2 + S3（限流可绕过 + 注册全开放）**：这两个组合起来，公网上的攻击者可以无成本爆破密码、无成本刷满上游接口配额。历史上"东财接口限流 → 页面 502"已经发生过。
2. **S1（Cookie 无 Secure）**：局域网内任何人抓一个包就能拿到 30 天会话，绕过所有密码强度。
3. **S4（JSON 静默损坏）**：这不是被攻击，是"哪天会自己坏"，而且坏的时候**没有任何日志**，是最难排查的一类故障。

### 2.2 暴露面收敛（Cloudflare 侧，不改代码）

- 开 **Always Use HTTPS** + **HSTS**。
- 对 `/api/auth/*` 加 **WAF 速率限制**（如 10 次/分钟/IP）。
- 可选 **Cloudflare Access**（Zero Trust 免费额度内），只放行你自己的邮箱登录隧道——这是"对外开放"与"只给自己用"之间性价比最高的一步（具体额度以 Cloudflare 控制台当前政策为准）。
- 隧道只发布 `8090`；`2323`（root shell）与 `9302`（dockerctl）**不要**挂到隧道上，保持 IP 白名单。

## 3. 为什么"换成 Java / .NET"不是安全方案

### 3.1 前后端职责边界

浏览器**只能**执行 HTML / CSS / JavaScript。无论后端是 Node、Java 还是 .NET，浏览器拿到的仍然是同一份 `index.html` + `app.js` + `app.css`。所以：

- "把系统重构成 Java/.NET" = **只换后端**，`public/` 那 7,265 行前端一行都不会变，XSS 面（S6）一分都不会减少。
- "HTML/JS 实现所以不安全"这个因果链不成立。真正决定安全的是：**传输是否加密、会话是否可窃取、鉴权是否在服务端、输入是否校验、暴露面是否最小**。

### 3.2 当前 15 项风险，换语言后是否消失

| 风险 | 换 Java/.NET 后 | 说明 |
| --- | --- | --- |
| S1 Cookie 无 `Secure` | ❌ 仍在 | 要自己配 |
| S2 限流可绕过 | ⚠️ 可能更好 | Spring Security / ASP.NET RateLimiter 有现成组件，但仍需正确配置"可信代理" |
| S3 注册开放 | ❌ 仍在 | 是业务开关，与语言无关 |
| S4 JSON 损坏 | ❌ 仍在 | 是"存储方式"问题，不是语言问题（换数据库才解决） |
| S5 安全头 | ❌ 仍在 | 要自己配 |
| S6 XSS 面 | ❌ 仍在 | 前端代码不变 |
| S7 CSRF / CORS | ⚠️ 可能更好 | 框架自带 CSRF 中间件，但换了框架仍要选对 |
| S8 路径穿越 | ⚠️ 可能更好 | 静态文件中间件通常更成熟 |
| S9 同步读盘 | ✅ 解决 | 但这是"存储改造"顺带解决的 |
| S10 SSRF | ❌ 仍在 | 要自己校验 |
| S11 上游超时 | ❌ 仍在 | 要自己加 |
| **新增：依赖攻击面** | ❌ **变差** | 现在**零 npm 依赖**；换 Spring Boot 会引入几十个传递依赖（Jackson、Tomcat、Logback…），换 ASP.NET 也会带一堆 NuGet——需要持续打补丁、跑 SCA 扫描，而当前是"零依赖、零升级负担" |

> 一句话：**重写能解决的只有 S9 和部分 S2/S7/S8，其余 10 项换个语言照样得一件件做。** 而重写会新增"几十个第三方依赖"这个当前不存在的攻击面。

### 3.3 结论

**不要为了安全而重写。** 安全该做的是 §2 的 15 项，工作量 1 天 + 1 天，与语言无关。重写是"架构/团队/规模"问题，见 §4.3 的触发条件。

## 4. 技术栈选型

### 4.1 三方案对比

| 维度 | A. 保留 Node + 加固 + 模块化（推荐） | B. Java 21 + Spring Boot 3 | C. .NET 8（ASP.NET Core Minimal API） |
| --- | --- | --- | --- |
| 代码迁移量 | 0（原地改） | 8,915 行后端全部重写 | 8,915 行后端全部重写 |
| 前端改动 | 0 | 0 | 0 |
| 等效工期（单人） | P0 1 天；P1 3–5 天；P2 5–8 天 | 10–14 周 | 8–12 周 |
| 期间线上可用性 | 可逐项灰度、随时回退 | 需两套并行、双写/切流 | 同 B |
| 最大风险 | 无（小步改动） | 行情解析口径回归、推送漏发 | 同 B |
| 依赖攻击面 | **零依赖** | 大（Maven 传递依赖） | 中（NuGet） |
| 运维 | 现状（`node server.js`） | 需 JVM + systemd 调优 | 需运行时（self-contained 单文件可免） |
| 团队可替换性 | 需要会 JS/Node | 招人容易 | 招人容易 |
| 多实例水平扩展 | 弱（单进程 + 文件） | 强 | 强 |
| 企业合规 / SSO | 需自己写 | 生态成熟 | 生态成熟 |

### 4.2 重写的真实成本拆解（为什么 8–14 周）

| 工作项 | 说明 | 占比 |
| --- | --- | --- |
| 上游行情口径 | 32 处出站调用：东财 push2 / 板块 / 资金流 / 基金 / 美股 Nasdaq、腾讯、新浪；GBK 解码、字段缺失兜底、降级链 | ~45% |
| 业务计算 | `lib/engine.js` + `lib/indicators.js`：评分、作战中心、板块确认、明日策略 | ~20% |
| 推送 | 14:30 持仓策略 / 19:30 净值，幂等（`lastSent`）、时区（东八区）、工作日判断、失败重试 | ~15% |
| 账号 / 会话 / 统计 / 后台 | 15 个端点 + 角色矩阵 + 统计聚合 | ~15% |
| 前端 | **0**（不动） | 0 |
| 上线切换 | 双跑对比、数据迁移、回滚预案 | ~5% |

最大代价不是人力，是 **14:30 / 19:30 推送漏发**——这是业务上不可接受的失败模式，而它在重写期间出现概率最高。

### 4.3 什么情况下才值得重写（决策闸门）

**满足任意一条再启动 P3：**

1. 需要**多实例 / 水平扩展**（SQLite 单写者到瓶颈，或要跨机器部署）；
2. 需要**企业级合规审计 / SSO / 多租户隔离**；
3. 前端要从当前单页改成 **SSR**（那才真的需要 Java/.NET 的模板或 Next.js 类方案）；
4. 维护者只剩**只招 Java 或只招 .NET** 的团队；
5. Node 生态出现**无法绕过的安全事件**（当前零依赖，概率极低）。

### 4.4 若真要重写：Strangler（绞杀者）路线

不要"停服重写"，按依赖倒序替换，每一步都可回滚：

```
第 1 步 存储先行：JSON → SQLite（本方案 P1，与语言无关，两边都能用）
第 2 步 鉴权抽离：新增一个薄网关（Nginx/Caddy 或 Java/.NET 写的 auth 服务）处理登录、Cookie、限流
第 3 步 只读接口迁移：行情类（无状态、可对比）→ 新服务，旧服务保留，逐接口灰度
第 4 步 有状态接口迁移：自选 / 持仓 / 推送配置（此时数据已在 SQLite，两边共库）
第 5 步 推送迁移：新旧双发 1 周对比（只记录不真发），确认一致后切换
第 6 步 下线 Node 服务
```

## 5. 存储选型

### 5.1 现状 JSON 的 5 个机制问题（不是"文件不好"，是这几个实现细节）

| # | 问题 | 证据 | 后果 |
| --- | --- | --- | --- |
| 1 | 非原子写 | `7573` `writeFileSync` 直接截断重写 | 写到一半崩溃 → 文件损坏 |
| 2 | 解析失败静默回退 | `7563-7569` `catch → fallback` | 损坏后变"空账号表"，不报警 |
| 3 | 读改写竞态 | `7690-7703` 全量读 `sessions` → 改 → 全量写 | 两个登录并发，后者覆盖前者，前者会话丢失 |
| 4 | 无查询能力 | `7821-7832` 统计全量读进内存再过滤 | 统计维度一多就慢，且 120 天全量常驻 |
| 5 | 每请求同步 IO | `7633-7646` | 阻塞事件循环（S9） |

### 5.2 四方案对比

| 维度 | 现状 JSON | **SQLite（推荐）** | MySQL | PostgreSQL |
| --- | --- | --- | --- | --- |
| 事务 / 崩溃一致性 | ❌ | ✅ WAL + 事务 | ✅ | ✅ |
| 并发写 | ❌ 后写覆盖 | ✅ 单写者 + `busy_timeout` | ✅ | ✅ |
| 查询 / 聚合 | ❌ 全量内存 | ✅ SQL + 索引 | ✅ | ✅ |
| 备份 | 拷贝目录 | `VACUUM INTO` 单文件 | 需 `mysqldump` | 需 `pg_dump` |
| 额外常驻服务 | 无 | **无** | 有（内存 200 MB+） | 有（内存 300 MB+） |
| 迁移改动面 | — | 小（**同步 API 对齐**） | 中（异步驱动 → 全链路 async） | 中 |
| 依赖 | 零 | **零**（`node:sqlite` 内置） | npm 驱动 | npm 驱动 |
| 规模上限 | 单进程小数据 | 单机（万级 QPS 前够用） | 大 | 大 |
| 当前规模是否合适 | 勉强 | **刚好** | 过重 | 过重 |

**为什么 SQLite 的"改动面小"是关键**：现有数据函数（`loadUsers` / `saveUsers` / `loadSessions` / `loadPortfolio`…）**全是同步函数**，`node:sqlite` 的 `DatabaseSync` 也是同步 API → 函数签名不用改，调用方一行不用动，前端零改动。换成 MySQL/PG 的异步驱动，会逼着把几十处调用链改成 `await`，这才是真正的大改。

### 5.3 边界原则：权威状态 vs 可再生缓存

| 类别 | 数据 | 去向 |
| --- | --- | --- |
| **权威状态**（丢了就麻烦） | 账号、会话、自选 / 持仓 / 自选股、推送配置、使用统计、登录事件、更新履历 | **进数据库** |
| **可再生缓存**（丢了下次抓就有） | `boards.json`、`sector-members.json`、`us-sessions.json`、`auction-*.json` | **留在文件 / 内存**，并按天淘汰 |

把 145 KB 的行情快照也塞进数据库是"为了统一而统一"：它们没有事务需求、没有查询需求、只有 TTL 需求，进库反而让备份变大、让每日清理变复杂。

### 5.4 前置条件（P1 开工前必须确认）

1. `node:sqlite` 需要 **Node ≥ 22.5**。本地已实测通过（v24.14.1，`DatabaseSync` 可直接用，会打印 `ExperimentalWarning`，可用 `--disable-warning=ExperimentalWarning` 静音）。**NAS 是 v20 → 必须先升级**。
2. 确认 NAS 架构：`uname -m`。若为 `aarch64`/`arm64`，官方 Node 24 Linux ARM64 包可用；若无法升级，退化方案为 `better-sqlite3`（需对应预编译二进制）或暂缓 P1。
3. 升级窗口：选在非交易日（周末），且**先备份** `data/` 与 `server.js`。
4. 备份策略同步调整：从"`tar data/`"改为"`sqlite3 gp.sqlite "VACUUM INTO '...'"`（或进程内定时任务），保留 7 天。

### 5.5 为什么不现在上 MySQL / PostgreSQL

当前：5 个账号（`data/users.json` 实测）、日请求约百级、权威数据 15 KB。MySQL/PG 会带来：一个要监控的常驻进程、一套要备份的库、一份要轮换的密码、一次 NAS 内存占用，换来的能力（多实例、大并发、复杂分析）当前用不到。**等到 §4.3 第 1 条成立时再迁移**——届时数据已在 SQLite，导出到 PG 是 `COPY` 级别的工作。

### 7.3 设计取舍

1. **唯一真源**：现在主账号持仓在 `push-config.json` 与 `userdata/<id>.json` 两处（`7719-7748` 专门写了镜像逻辑）。改造后只有 `portfolio_*` 一张表，`push_config` 不再存持仓 → 少一处双写、少一类"推送和页面不一致"的 bug。
2. **会话存哈希**：`sha256(token)` 为键。文件/库泄露 ≠ 可直接登录。代价是"按 token 查不到原文"，但本来也不需要原文。
3. **`slots_json` 用 JSON 列**：推送时段是固定 2 条的小数组、无查询需求、结构由前端与后端共同约定 → 拆表收益为零，保持 JSON 列。
4. **统计三表拆分**：现在是 `days[day][userId]` 嵌套对象，查询"某用户 7 天曲线"要全量遍历；拆表后一条 SQL 搞定，也让 `stats.json` 那个 2 MB 级别的文件不再全量常驻内存。
5. **时间字段**：`created_at` 等用 ISO 字符串（与现有 JSON 一致，便于对比校验），`sessions` / `stats` 用毫秒整数（本来就是数字）。

### 7.4 容量估算

- 账号：每人 ~300 B → 100 账号 30 KB。
- 会话：每人 1–3 条，30 天过期清理 → 千级行。
- 统计：3 表 × 120 天 × 账号数 → 万级行，SQLite 毫无压力。
- 结论：`gp.sqlite` 预计 **< 5 MB**，远小于现在的 `us-sessions.json` 单文件。

## 8. 迁移与校验流程

### 8.1 前置

```bash
# 1) 确认 Node 与架构（NAS 上执行）
node -v          # 需要 >= 22.5
uname -m         # aarch64 / x86_64

# 2) 备份（NAS 上执行）
systemctl stop gp-terminal
tar czf /data/backup/gp-data/pre-sqlite-$(date +%Y%m%d-%H%M).tar.gz -C /data/gp-terminal data server.js
```

### 8.2 步骤

| 步 | 动作 | 校验 |
| --- | --- | --- |
| 1 | 停服（或只读模式） | 页面不可写 |
| 2 | `node scripts/migrate-json-to-sqlite.mjs --dry-run` | 打印将导入的行数与差异，不写库 |
| 3 | 正式导入（幂等：`INSERT OR IGNORE`） | 退出码 0 |
| 4 | `--verify`：逐表比对计数、哈希、深度相等 | 全部 `OK` |
| 5 | 以 `STORE=sqlite` 启动 | 启动日志打印 `store: sqlite` |
| 6 | 冒烟：登录 → 自选 → 持仓 → 刷新 → 后台 → 推送预览 | §9 清单前 8 条 |
| 7 | 观察 30 分钟：错误率、`502` 数、`gp.sqlite-wal` 大小 | 无新增 `[API ERROR]` |
| 8 | 保留旧 JSON 文件 **不删**，标记 `data/json-frozen-<date>/` | 回滚可用 |

### 8.3 校验清单（`--verify` 必须覆盖）

- 账号：行数、`username` 集合、每条 `hash` 与 `salt` **逐字节相等**、`role` / `is_primary` 相等。
- 持仓：每个用户 `funds` 的**顺序**、`holdings` 的键值、`watchlist` 相等。
- 会话：条数、`expiresAt` 相等；抽一条旧 token 验证仍能 `currentUser()`。
- 推送：除 `funds/holdings` 外所有字段深度相等；`lastSent` / `lastResult` / `followUp` 结构不变。
- 统计：`Σrequests`、`Σbytes`、`Σlogins`、`logins.length` 与迁移前一致。
- 负面用例：库文件损坏时，启动必须**报错并拒绝写**，而不是静默当空表（对比现状 §5.1 第 2 条）。

### 8.4 回滚

1. `systemctl stop gp-terminal`
2. `STORE=json`（`/etc/systemd/system/gp-terminal.service` 的 `Environment=` 一行）
3. `systemctl start gp-terminal`
4. 旧 JSON 在迁移期间**只读**，因此回滚后数据完整；`gp.sqlite` 可保留待查或删除。

### 8.5 上线后观察指标

| 指标 | 采集方式 | 目标 |
| --- | --- | --- |
| API 错误率 | `server.out.log` 里 `[API ERROR]` 计数 | 与迁移前持平 |
| 登录成功率 | `login_events` 按 `ok` 分组 | ≥ 迁移前 |
| 平均响应时间 | 现有日志里的 `Nms` | 不劣化 |
| DB 大小 | `ls -l data/gp.sqlite*` | < 10 MB |
| 推送准时 | `push_config.last_result_json.at` 与 14:30 / 19:30 偏差 | < 2 分钟 |
